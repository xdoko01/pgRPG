## An entity definition

```jsonc
{
    "id": "crate01",
    "templates": ["t_crate", "t_tile_pos(4, 3, game_sokoban_lvl01)"],
    "components": [
        {"type": "position:Position", "params": {"tile_x": 5, "tile_y": 5, "map": "arena"}}
    ],
    "remove": [{"type": "movable:Movable"}]
}
```

Applied by `_update_entity` in exactly this order:

1. **`templates`**, in list order. Each template's components are added. **Later wins** — a second
   template's `Position` replaces the first's, because `World.add_component` replaces by type.
2. **`components`**, added next, so they override anything a template supplied.
3. **`remove`**, each `{"type": ...}` removed. Supported by the loader; **no shipped scene uses it**.

`id` is required. It is the entity's **alias** — see [../_shared/aliases.md](../_shared/aliases.md).

## Template resolution — three places, one syntax

A template reference is resolved by `get_dict_params` → `get_dict`, which looks in **storage first,
then the filesystem**:

1. `ecs_manager._template_definitions` — everything from a scene's `templates` key, plus every entity
   definition already loaded.
2. A file under `FILEPATHS["ENTITY_PATH"]` (`example_game/resources/entities/`), path-addressed with
   `/`, extension optional.

So these are all valid in the same `templates` list:

```jsonc
"templates": [
    "t_crate",                                 // scene-level template, by id
    "model/body/male/human/white",             // file: resources/entities/model/body/male/human/white.json
    "crate01",                                 // another entity, by alias
    "t_tile_pos(4, 3, game_sokoban_lvl01)"     // template call with positional args
]
```

`get_dict` uses `get_dict_value(d=storage, path=dictpath, sep='/')` for the storage lookup, so a
`/`-separated id navigates *nested keys in storage* as well as directories on disk — but in practice
storage is flat (id → definition), so a `/` path falls through to the filesystem.

> ⚠️ Storage wins. An entity or scene template whose id happens to match a file path shadows the
> file. Since **every loaded entity is registered as a template under its own alias**, an entity
> named e.g. `model/body/male/human/white` would shadow that file. Keep entity aliases and template
> file paths in distinct namespaces.

## Template files

A template file is just an entity definition, usually with an `id`, optional `vars`, optional nested
`templates`, and `components`:

`resources/entities/model/body/male/human/white.json`:

```json
{
    "id": "male_human_white_model",
    "templates": ["model/body/male/human"],
    "components": [
        {"type": "renderable_model:RenderableModel",
         "params": {"model": "generic/body/male/body_male_human_white.json"}}
    ]
}
```

Templates nest: this one pulls in `model/body/male/human` first. Nesting is resolved recursively by
`load_stored_template` → `_update_entity` → `load_stored_template`.

The `id` inside a template file is **not** how you reference it — you reference it by *path*. The
internal `id` is cosmetic (and is what the definition would be registered under if the file were
loaded as an entity).

`resources/entities/` is organised by kind: `model/` (sprite bindings), `thing/` (game objects),
`behavior/` (AI), `controls/` (input bindings), `effects/`, `_special/`. There are ~2 500 files, most
of them one-line model bindings generated by `pgrpg/utils/generate_model_json_from_template.py`.

## Parameterised templates: `vars` and `$`

A template declares its parameters in `vars`, using `$name` and optional `=default`:

```jsonc
{
    "id": "t_tile_pos",
    "vars": ["$tileX=0", "$tileY=0", "$map"],
    "components": [
        {"type": "position:Position",
         "params": {"tile_x": "$tileX", "tile_y": "$tileY", "map": "$map"}}
    ]
}
```

`get_dict_params` parses the call, builds a translation dict, and runs `translate` over the whole
template body — so `$name` is substituted **anywhere** it appears, at any depth, in keys or values.

### Call forms

All of these produce the same result (verified by the doctests in
`pgrpg/functions/get_dict_params.py`):

```jsonc
"t_tile_pos(5, 5, test_arena_sand)"                       // positional
"t_tile_pos(5, 5, $map=test_arena_sand)"                  // mixed
"t_tile_pos($tileX = 5, $tileY=2, $map=test_arena_sand)"  // all keyword; whitespace ok
["t_tile_pos", [5, 2, "test_arena_sand"]]                 // list form, positional
["t_tile_pos", {"$tileX": 5, "$tileY": 2, "$map": "test_arena_sand"}]   // list form, keyword
["t_tile_pos", [3, 4, 5], {"$tileX": 5, "$tileY": 2, "$map": "arena"}]  // list form, both
```

These six are the whole set — `parse_fnc_list` accepts `[name]`, `[name, [args]]`,
`[name, {kwargs}]` and `[name, [args], {kwargs}]`, and nothing else. Since #95 the schemas enforce
exactly that set, through the single `definitions.schema.json#/definitions/template_ref` that both
`entity.schema.json` and `template.schema.json` reference — so an editor now flags a malformed call.
See [schemas.md](schemas.md#one-template-reference-definition-not-two).

The list form is what you need when an argument is not a scalar — a list of checkpoints, say:

```jsonc
["behavior/guard_fight_back_if_ambushed_and_attack_on_sight_or_hear", [],
 {"$checkpoints": [[5,5], [30,10], [50,50], [50,5]], "$enemies": ["player01"]}]
```

### Argument precedence

`get_dict_params` builds the substitution dict as:

```python
d_trans = {**vars_kwargs, **d_from_args, **kwargs}
```

1. **Lowest** — defaults declared in `vars` (`$tileX=0`).
2. **Middle** — positional arguments, zipped against `vars` in order and **truncated to
   `len(vars)`**, so surplus positional arguments are silently discarded.
   `t_tile_pos(1, 2, 3, 4, 5, $map=x)` uses only `1, 2` and the keyword `$map`.
3. **Highest** — keyword arguments.

Values are type-converted by `convert_str`, which `eval`s the token: `"5"` → `5`, `"1.52"` → `1.52`,
`'[1, 2]'` → `[1, 2]`, and a bare word stays a string. So `t_tile_pos(5, 5, arena)` really does pass
integers.

> ⚠️ `convert_str` uses `eval`. A template argument is evaluated as Python. Only `NameError` and
> `SyntaxError` are caught, so anything else (e.g. a `ZeroDivisionError` in an argument) propagates.

### Substitution is textual and total

`translate` replaces any value **equal to** `"$tileX"`. It does not do partial-string interpolation —
`"tile_$tileX"` is not substituted. Use whole-value placeholders.

An unmatched `$var` survives into the component params as the literal string `"$tileX"`, which then
fails the component's `isinstance` assertion. That is the usual cause of a `ValueError` naming a
component whose params look fine.

## Every entity becomes a template

`load_update_empty_entity(entity_def, add_to_templates=True)` ends with:

```python
if add_to_templates: load_template(template_def=entity_def)
```

So after `crate01` is loaded, `"crate01"` is a valid template id. `sokoban_level01.jsonc` uses this
four ways in one file:

```jsonc
// 1. template + parameterised template
{"id": "crate01", "templates": ["t_crate", "t_tile_pos(4, 3, game_sokoban_lvl01)"]}

// 2. an existing entity as a template + a parameterised one
{"id": "crate02", "templates": ["crate01", "t_tile_pos(5, 4, game_sokoban_lvl01)"]}

// 3. template + an explicit component
{"id": "crate03", "templates": ["t_crate"],
 "components": [{"type": "position:Position", "params": {"tile_x": 5, "tile_y": 5, "map": "..."}}]}

// 4. an existing entity + an overriding component
{"id": "crate04", "templates": ["crate01"],
 "components": [{"type": "position:Position", "params": {"tile_x": 6, "tile_y": 7, "map": "..."}}]}
```

Two consequences:

- **Order matters for entity-as-template.** `crate02` can only clone `crate01` because `crate01`
  appears earlier in the `entities` list — pass 2 fills entities in list order. This is the one place
  where entity order is significant; alias *references* are order-independent, template
  *inheritance* is not.
- **A definition, not a snapshot.** The stored template is the entity's JSON definition, so cloning
  replays the definition rather than copying live component state.

## Runtime-created entities

`Factory`-generated entities (projectiles, effects) carry a full entity definition in their
`prescription` param and are created by `ecs_manager.create_entity` in a single pass:

```jsonc
{"type": "factory:Factory", "params": {
    "prescription": {
        "id": "wooden_arrows_pack_arrow",
        "templates": ["model/ammo/shoot/wooden_arrow"],
        "components": [
            {"type": "damaging:Damaging", "params": {"damage": 25}},
            {"type": "movable:Movable",   "params": {"velocity": 500, "accelerate": -2}},
            {"type": "destroy_on_collision:DestroyOnCollision", "params": {"ttl": 0}}
        ]
    }
}}
```

Because creation is single-pass, a prescription's params can only reference aliases that already
exist. Also note the `id` is reused by every arrow — `_create_empty_entity` returns the **existing**
entity for a known alias, so a prescription with a fixed `id` recycles one entity rather than
spawning many. `create_entity` accepts an `entity_alias` override for that reason, and
`PerformFactoryGenerationProcessor` is where to look for how the example game handles it.
